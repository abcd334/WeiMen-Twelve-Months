## 1. v0.5 現有架構

| 層次 | 現況與責任 | v0.6 處理 |
|---|---|---|
| `app.py` | Streamlit session；問題文字、四人觀點、調查方向、門務方案、派遣、夜談、推理與問卷 | false_cards 改成一個核心問題、一個案件行動；其他故事線保留舊畫面 |
| `models.py` | GameState、Character、Cue；公開投影白名單 | 新增案件狀態，保留公開／私有隔離 |
| `game_engine.py` | 隨機人物、月份維持費、事件排程、派遣結算、傷疲、關係、夜景、永久後果、結局 | 保留遊戲規則與 phase；案件選擇交給 case_engine |
| `investigation.py` | 月份覆寫、調查選項、證據儲存、補證與推理判定 | 共用證據板與推理；舊調查介面僅供另外兩線使用 |
| `narrative.py` | 接受公開 context，穩定選擇完整句型；不消耗遊戲 RNG | 保留純呈現，改收帶來源的案件／夜景 context |
| `data_loader.py` | 快取 JSON、驗證角色觀點／事件／證據圖 | 增加依故事引擎版本分流的案件驗證 |
| `game_runtime.py` | 在 UI 綁定引擎前刷新過期模組 | 納入新模組和資料快取的依賴順序 |
| 模擬與 tests | 公開資訊策略、重現、敘事覆蓋、Streamlit 全流程 | 更新 action 紀錄、因果驗證與兩軸結局統計 |

目前一般流程為：`new_game → begin_month → resolve_day → start_night → resolve_night → begin_month`。第 4／8／11 月在夜談完成後，`begin_month` 才切到 `deduction`；推理完成再前進。第 12 月沒有一般派遣，進月後直接判定結局。

值得保留的基礎：調查明確指定 targets、證據／說法／待查分開存放、已得證據不因失敗刪除、補證可穩定取得、推理僅接受已得資料、重複與過期提交防護、NPC／弟子分離，以及永久後果的跨月預警。

**與規格問題描述需要區分的現況：** false_cards 已有 1～11 月 `monthly_scenes` 覆寫，第 12 月使用固定 finale。正常現有資料下，並不是每月仍在隨機抽 generic mission；缺口是「按月覆寫」仍然沿用部分基礎事件內容，且不會根據上個選擇決定下一集。v0.6 必須進一步禁止這條線進入隨機 fallback，並驗證缺月即資料錯誤。

## 2. 造成斷裂的實際 code paths

以下行號以本次檢視基準為準。

| 問題 | 實際路徑 | 遊戲中的結果 |
|---|---|---|
| 核心問題只是字串 | `app.py:105` 顯示 `event.current_question`；`game_engine.py:313` 直接投影事件資料；`models.py:122` 起的 GameState 沒有問題狀態 | 沒有問題 ID、子問題完成度或已知事實來源，選項不由問題推導 |

## 3. v0.6 遷移與程式設計

### 3.1 模組責任與狀態所有權

新增 `case_models.py`：定義 `CaseQuestion`、`CaseAction`，以及 `DayContext`／hook 的型別契約。前兩者使用 dataclass；DayContext 可用 TypedDict，保留規格的 dict 操作方式，不增加外部依賴。

新增 `case_engine.py`：提供 `current_episode`、`current_question`、`available_case_actions`、`select_next_episode`、`build_night_from_day_context`、問題進度計算及公開投影。核心規則收資料與公開結果；不反向匯入 game_engine。

`game_engine.py` 負責唯一的提交與 phase 推進入口，組合案例計畫和共用資源／人物結算，再呼叫 investigation 儲存證據。避免 case_engine、investigation、game_engine 形成新循環相依。可逐步讓 investigation 的儲存／推理函式回傳結果，由引擎統一建立 fact、decision 和 callback。

GameState 新增規格要求的 `current_question_id`、`case_history`、`day_context`、`next_hooks`、`case_progress`、`public_strategy`。另保存 `current_episode_id`，用它固定當月 episode／variant；UI rerun 不重新選事件。結局保存 `mystery_axis`／`sect_axis` 及可公開的判定原因。

`case_progress[question_id]` 保存已回答子問題、證據來源 ID 與 open／partial／resolved。沒有經核實的回答為 open；部分子問題核實為 partial；達到該問題宣告的必要條件才 resolved。下一月可推進，舊問題仍保留未解部分，不能以「月份過了」當成查明。

### 3.2 單一問題、單一行動

每個 episode 宣告唯一 question 和 action_ids；只有其行動可被提交。每個 action 的 question_part 必須對應這個問題的子項。已解子項可保留「複核」行動，但明示已查過、不重發獎勵。

對 false_cards 提供 `resolve_case_action(state, action_id, participant_ids, token)` 與 `legal_case_actions(state)`，不接受 focus／mission 的第二組輸入。舊 `resolve_day` 只服務舊線，false_cards 誤入時明確拒絕，避免模擬器仍偷偷走雙選。

CaseAction 保留規格欄位，另於內部規則提供：取得條件、成功／失敗結果、穩定查證管道、延遲效果和情境 tags。UI 白名單只顯示方法、要回答的子問題、專長、人數、成本與風險；possible_evidence 只呈現「預期可核對材料」，不顯示尚未取得的結論、supports／contradicts 或隱藏成功率。

提交時先完整驗證 phase、token、當月行動、隊員唯一性／資格、成本和前提，再消耗 RNG／資源。隊員用既有角色順序排序，同一隊不同點選順序不改結果。只扣一次案件行動成本。

任務結果與證據核查都來自同一 CaseAction。可靠簿冊、補證可採穩定核查；冒險追人可能留下待查線索。禁止以無關門務成功開啟證據，亦禁止用信任、忠誠或對外通信直接判定案件真偽。

### 3.3 DayContext 與 hook 契約

DayContext 依規格保存 month、episode_id、question_id、action_id、participants、success、evidence_gained、claims_gained、resources_changed、injuries、relationship_changes、next_hooks。補上 `lead_ids`、`fact_ids`、`context_tags`、`deduction_result`，讓失敗、推理和無新證據的處理也可追溯。

resources_changed 使用實際結算前後差值，包含成本與結果，不拿未經 clamp 的規則數字充當實際變化。injuries／relationship_changes 只記本次增量；歷史舊傷不能冒充今天新受傷。原始人物數值仍留在內部，夜景呈現只收到可見狀態與有來源的描述。

DayContext 在白天結算完成時定稿並拷貝到 case_history。夜間結果另記歷史；不回寫「白天曾發生什麼」。夜間選擇以原 day_context 為來源產生新的 next_hooks，供下一月使用。

hook 定義用穩定 ID；實例保存 `source_month`、`source_phase`、`source_fact_ids`、`target_episode`、`due_month`、`priority`、`payload` 和 consumed 狀態。payload 僅接受已知資料；互斥回應用同一 group 去重。消費一次，未到期不提前觸發。來源角色離門時改成留下的記錄／合法替代人，不讓缺席者親自發言。

下一集挑選：符合目標月的 previous consequence → required case episode → character consequence；同優先序以宣告順序和 hook ID 排序，不抽 RNG。固定十二月骨架，後果選擇該月的場景變體／可用方法／NPC 回應；不讓支線占掉第 4／8／11 月推理或第 10 月補證。

required episode 也必須有前月「尚待答覆／新材料送達／期限迫近」的來源 hook，不能只有日期。成功／失敗／保留／休整都產生合理承接。第一月是明確的起始事件例外。這使同月骨架可重現，玩家決策仍真正在改下一集。

每格產出是可能查得的資料，不是按月自動頒發。例如第 1 月只問經手人，當晚不能說「印記已核實異常」；第 2 月開場只可說找到簿冊／待核簽名，玩家未查以前不能替其確認缺漏。第 10 月未取得 courier_lead 的路線，先由第九月留下的交接紀錄和公開徵詢找到可問的人，不能假稱玩家之前已跟蹤成功。

### 3.5 推理先於夜談

建議 false_cards 在第 4／8／11 月將 deduction 作為**當日的核心處理**，由當場 NPC 提出。該日不另附一個門務任務，不要求為掌門的表態虛構派遣。這三集的 question.action_ids 指向推理型 CaseAction；內部增加 `kind=deduction`，team_size=0、cost=0，資料驗證明確限制這個例外。一般調查仍派 1～2 人。

phase：一般月 `day → day_result → night → night_result → 下一月`；推理月 `deduction → deduction_result → night → night_result → 下一月`。新局／進月仍顯示事件、核心問題、已知資料、四名弟子看法，接著呈現劇情人物的提問與輸入。兩條舊線保持原 phase 次序。

推理結算也產生 DayContext；不得因 `accepted=True` 的「證據不足」而當成查明。歷史分開記錄提交合法、論點有支持與是否保留判斷。第 11 月已知部分的提交也保存實際選出的資料，不像現有 UI 一勾保留就把 chosen 清空；只有完整正確三件鏈可滿足 complete。

### 3.6 由當日後果選夜景

一般夜晚依重大證據 → 任務失敗 → 新受傷 → 利益／關係衝突 → 背景相符私人 arc → quiet 排序。命中多項時主題取最高優先，其餘作有來源的附段，例如取得重要證據但同行受傷，仍應交代傷者與可用照護回應，不能吞掉受傷後果。

第 4／8 月以剛完成的 deduction_result 產生主題。第 11 月 episode／最終提交產生 `final_council` context，由它觸發全員共同夜談；不是重建月曆式 night kind。發言僅引用已查明範圍；缺席者保留空位記憶。

私人 arc 必須同時符合 trigger_context、角色既有背景／經歷、角色仍在場和可推進 stage。不得因公開背景是商賈就新造一筆家債。重大證據夜晚也可讓符合背景的弟子自然補充，但實際進入私人選擇、回應完成後才推進私人 arc。

第 1 月的「公開／保留／第二人複核」分別生成公開範圍、延後說明或複核安排的事實和 hook，實際改變程守禾下月的要求／行動條件與信任反應。複核僅補既有證據的佐證來源；不能把沒有取得的核心證據在夜間補發。證據事實不隨公開策略變真或變假。

無合法出勤時保留休整出口；其 DayContext 記錄暫緩、未解問題、資源代價及下一步催辦。角色全重傷不應讓夜景建立失敗。沒有合法夜談付費選項時至少有零成本回應。

### 3.7 結局與資源平衡

先獨立計算兩軸，再映射標題，不以證據直接蓋過門派狀態。

Mystery：完整核心證據與第十一月正確組鏈為 complete；至少有一項與責任判斷直接相關的已驗證核心資料、但鏈不足為 partial；只有說法／待查或無核心資料為 unresolved。動機或關係線索本身不算洗清責任。

Sect 初始判準提案：仍沿用糧餉耗盡、無人在門及敵對事件防備耗盡的提前覆滅規則；第十二月至少兩人留門，且 defense ≥45 或 reputation ≥50 才可守住。守住後，至少三人留門、兩人可派遣、defense ≥60 且留門角色間沒有 value <−15 的既有嚴重關係衝突，才是 stable；其餘為 weakened。這些閾值需經新收入／傷疲模擬調整，不直接宣稱已平衡。

| Mystery ＼ Sect | stable | weakened | collapsed |
|---|---|---|---|
| complete | 揭破陰謀 | 查對案件但門派失和 | 門派覆滅；附已查明案件回顧 |
| partial | 洗清部分責任 | 洗清部分責任；附守山代價 | 門派覆滅；附已知與缺口 |
| unresolved | 真相未明但守住山門 | 真相未明但守住山門；附守山代價 | 門派覆滅；附未解記錄 |

weakened 可能來自人手或守備受損；對應第四類結局的內文須說明真實原因，不能在沒有關係衝突時硬寫同門失和。兩軸及原因一併公開，標題不能取代原因。

最後的保人／守山／揭真相決定呈現順序與行動安排，不直接將兩軸改成成功。完整鏈證明假帖及交付事實；若缺 motive_evidence／delivery_link，結局不得額外宣稱已證明幕後授意細節。前掌門離山的敘述亦需該局實際取得留記，不能單憑三件核心證據把整份作者謎底貼出。

**收入要隨行動一起設計。** 目前初始糧餉 50，每月維持費 3，十二月維持費共 36，僅餘 14。若八個調查月每次花 2，即需 16，尚未算夜談；取消舊門務收入而只新增調查成本，會形成結構性缺糧。案件行動應提供有劇情來源的退回重複款項、查證報酬、共同負擔車馬費或節省守備成本，並給零成本保守方法。金錢效果與證據取得條件分開，不讓「花最多＝必然真相」成為唯一策略。

### 3.8 程式碼優化範圍

`resolve_day` 內多次呼叫 current_event，每次都可能深拷貝 overlay；新版每次提交建立一次 episode／action／合法隊伍索引，結算與敘事共用。公開投影同理只建立一次當月資料，避免同一 rerun 重複枚舉隊伍。這是可移除的重複工作，尚未做效能量測，不能宣稱已有速度提升。

靜態 thread／episode／evidence ID 索引可隨 JSON 快取；動態 legal_actions、公開人物狀態、current_question 不跨提交快取，避免舊傷勢／糧餉使行動錯誤放行。回傳玩家的 dict／list 仍須獨立拷貝。

資料校驗改用帶 thread、episode、欄位路徑的明確錯誤；新案件不用固定「每事件三選項」「輔助證據只能 2～4 件」等不適用的數量斷言。先抽共用規則再加入新分支，避免複製一整份 500 行的遊戲結算。

## 4. 資料遷移計畫

`story_threads.json` 為 false_cards 加 `engine: causal_v06`、questions、actions、episodes、hook definitions。用完整 episode 取代執行期 monthly_scenes overlay；其他兩線資料不改語義。遷移完成後刪除 false_cards 舊 monthly_scenes／investigations 中不再使用的資料，避免兩份案件來源逐漸不一致。

新增校驗：12 月集數完整、每集一題、action 問題部位合法、每個 target／hook 可解析、來源類型一致、所有成功／失敗／休整有承接、hook 不跨錯誤月份或循環耗盡、核心證據第十月均有替代來源、正文不能引用尚未滿足的證據條件。作者真相欄位不進公開投影。

第十月補證涵蓋三項核心證據所有缺失組合：個別補件與一個「逐項補查所有缺件」行動，讓一個白天仍能補足多類。補證依獨立封存／第二見證來源取得，保留原有證據，按不同來源寫清楚，不將所有補件偽裝成同一人交出原件。第十一月保留最後的送件安排作容錯時，必須是第十月實際建立的 hook，而非無因自動補齊。

版本統一升至 0.6：models、app、runtime 預期值、模擬報告和閱讀稿 metadata。已在進行的 0.5 session 保留到玩家選擇開始新版；重開沿用 seed，不移植證據或推理結果。舊問卷保持原 version。閱讀稿／行動回放加 game_version 和 action schema，0.5 的 option＋focus 不推測轉成 0.6 action；舊報告保留，0.6 報告另存版本目錄。

## 5. 向後相容風險與處理

| 風險 | 處理與驗證 |

| 全域移除舊調查 API 破壞另外兩線 | 以 thread.engine 分流，先保留 legacy API；舊線完整跑完及資料雜湊／遊玩結果比對 |

| 精確種子結果改变 | 保持角色生成及選線 RNG 順序；新案件採穩定排序。只承諾同版本 seed＋記錄行動可重現；舊線盡量保持既有序列 |
| 覆寫快取污染其他局 | 只快取靜態定義；runtime 新模組依賴順序納入刷新測試；投影不可改到遊戲本體 |

回歸保留：相同版本 seed＋相同行動和重複讀取決定性；token／重複提交／錯誤隊員／不足成本不更動狀態；public/private boundary；NPC 不進派遣；外部聯絡不是背叛；永久離門／倒戈至少兩個較早月份預警，其中一項可核實；普通風險不致死。

需要調整的現有測試與工具：`tests/test_app.py` 的 focus／plan widget 與版本字串；`tests/test_game_runtime.py` 的刷新清單和首局派遣；`tests/test_investigation.py` 的 false_cards witness 特例改為單 action；`tests/test_narrative.py` 的夜景種類配額改為因果來源；`tests/test_endings.py` 分開測新雙軸與舊優先序。simulate_balance／review_playthroughs 的 choose_focus 只走 legacy，case policy 只讀公開 action。audit_narrative 改讀 action_id／source IDs，不能仍用 focus_id 前綴推測補證。

因果承接率：分母為實際完成的 false_cards 夜談數；分子必須同時有當月 day_context 來源、有該日真實 fact／deduction ID，且內容與可選回應使用該結果。quiet 或只掛一個 source ID 的模板不算。完整十二月通常有 11 晚，至少 9 晚直接承接才達 80%；提前結束另外報告，分母為零記 N/A。

驗證順序：新資料／規則單測 → 三線 Streamlit 全流程與舊 session 重開 → 全套 pytest → 200 seed 敘事稽核 → 四種公開策略各 250 局平衡模擬 → 三線閱讀稿及 false_cards 分支閱讀稿人工逐段檢查。模擬不補滿資源、不跳月份；底層邊界單測可使用受控 fixture，但不可拿它作正常可玩證明。

交付應包含成功查明、保留判斷、查證失敗後補救、證據完整但門派受損的閱讀稿，以及每條 action → fact → night → hook → episode 的來源鏈。真人試玩才能驗證「玩家知道正在查什麼」，自動化指標不能代替理解度驗收。

## 確認後的實作順序

1. 建立 case_models、案例資料驗證和 false_cards 完整十二集資料；先使問題與行動一對一可追溯。
2. 實作單一 CaseAction 提交、共用資源／人物後果、DayContext 與補證；三線 API 分流。
3. 實作 hook 選下一集、日間推理、後果夜談與 trigger_context 私人事件。
4. 整合 UI、雙軸結局、版本刷新／重開與公開資訊回放工具。
5. 完成回歸、平衡及敘事驗證，再依實際結果調整費用和閾值。
